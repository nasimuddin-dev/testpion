# Scalability and architecture review (2026-10-22, commit 4d4b21a8)

Read-only review of TestPion against the cloud-ready design (docs/architecture/design.md §Cloud-ready design, planning/cloud-platform.md): the UI talks to the engine only over RPC, the engine is host-agnostic behind `WorkspaceStore` / `MetaStore` / `SecretStore`, multi-user (per-user workspaces, concurrent sessions), server-safe (no process-wide mutable state, bounded memory, no synchronous fs on hot paths). Every claim below was verified by reading the file at the cited line unless marked *unverified*.

Severity: **P0** blocks the cloud / multi-user version or breaks at 10k items · **P1** limits scale or costs a lot on a server · **P2** hygiene.

Scope read: `docs/architecture/*.md`, `planning/master-roadmap.md`, `planning/cloud-platform.md`, `tests/unit/architecture.test.ts`, `tests/unit/import-graph.test.ts`, `tests/unit/rpc-params-coverage.test.ts`, `tests/unit/core-scale.test.ts`, `tests/unit/desktop-scale-handlers.test.ts`, `tests/unit/backend-caches.test.ts`, `apps/desktop/backend/{backend,own-writes,stats-cache,console-log,run-data,web-server}.ts`, `apps/desktop/electron/{main,preload}.ts`, `apps/desktop/src/api.ts`, `packages/core/src/storage/{workspace,fsutil,metastore,workspace-watcher,app-dir}.ts`, `packages/core/src/net/{proxy,policy,production-guard}.ts`, `packages/core/src/scripts/sandbox.ts`, `packages/core/src/protocols/http/client.ts`, `packages/core/src/runner/{runner,run-results,monitors}.ts`, `packages/core/src/kinds/registry.ts`, plus greps over `packages/*/src`, `apps/desktop/backend`, `apps/desktop/src`.

Sync fs **on the request path** (verified): every send builds an engine context (`backend.ts:584-614` → `packages/core/src/engine.ts:18-26`) which calls `store.environmentView` (`workspace.ts:245-254`: `readdirSync` + one `statSync` per environment file, every call) and `store.collectionView` → `collectionFile` (`workspace.ts:190-205`: `existsSync`, then if the file is not named by id, **reads the text of every collection file** to find it) → `readJsonShared` (`statSync`). Text and parsed documents are cached (`fsutil.ts:418-535`), so the parse is amortised, but the stat/readdir syscalls happen on the main thread per send. On a desktop this is milliseconds; on a server it is the event loop of every tenant.

Also on the main thread: `fsutil.ts:382` `Atomics.wait(...)` — a **synchronous sleep of up to 50+100+200+400+700 = 1.45 s** when Windows refuses a rename (comment at `:355-358`), blocking the whole process.

**The per-session context already half exists.** `Backend` (`backend.ts:180-234`) is the session: store, secrets, settings, current values, cookie jar, search, run registry, controllers, MCP / WebSocket / Socket.IO / MQTT / Kafka sessions, mocks, GraphQL mock, subscriptions, recorder, debugger, monitors, terminals, console and log buffers, viz pages. `invoke` (`backend.ts:539-572`) already wraps every call in `AsyncLocalStorage` for own-writes and production consent. What is missing is the split into three objects:

```
AppServices   (one per process)   host, logger sinks, examplesDir, update checks, sandbox pool, net defaults
Session       (one per user+workspace)  everything Backend holds today, minus the above; its own data.changed epoch and event sink
RequestContext (one per RPC call, in AsyncLocalStorage)  user, permissions (`can`), allowProduction, AbortSignal, ownWrites batch, trace id
```

Handlers keep their signature `(be: Session)`; `RequestContext` is read through `currentCall()` where needed (signal, user) so the 44 handler modules do not all change at once. CLD-001 ("every handler receives a context … no handler reads globals") maps onto exactly this.

Guard test: `tests/unit/two-sessions.test.ts` constructs two `Backend`s in one process on two workspaces, sends one request from each with different proxy settings and different `ai` settings, runs a script in each concurrently, starts a fuzz in each; asserts no cross-talk (the proxy generation seen by each dispatcher, the script outputs, both fuzz runs finish). Today it would fail on proxy and fuzz.

## Proposed sequence

1. **Context first (small, 2-3 days):** `RequestContext` in ALS inside `invoke` (signal, user = local, `allowProduction` moved into it), `Session` extracted from `Backend` (the fields; handlers unchanged), per-session `fuzz`/`import`/`told` state. Write `two-sessions.test.ts` now; it documents the remaining globals (proxy, sandbox) as expected failures.
   *Why first:* cheap, no behaviour change, and every later refactor needs the test.
2. **Network config per context (2 days):** `NetConfig` in `ExecServices`; `dispatcherFor(spec, net)`; `setGlobalDispatcher` only in the CLI entry. Turns the two-sessions test green for proxies.
3. **Async store interfaces (2-3 weeks, mechanical):** `storage/interfaces.ts`; `FileWorkspaceStore` wraps the sync class; type `Backend.ws` and `ContextOptions.store` as the interface; convert handlers → runner → AI → MCP tools; the CLI keeps the sync class until last. Ship behind the same tests; the store-contract suite runs against files and memory. Also replace `Atomics.wait` with an async retry in the backend's write path.
   *Why third:* it is the gate for every cloud storage item and it is easier once the context (1) gives handlers a place to await from.
4. **Revisions + conflict errors (1 week):** `expectedVersion` on `saveCollection`/`saveEnvironment`/`saveLibrary`, `ConflictError`, meta into SQLite; the renderer sends its base version and reuses the merge screen. Then `col.patch` ops (the CLD-002 operation log) so the sync service has its unit.
5. **Retention and lazy reports (3 days):** `keepRuns`/`keepRunsDays` in `recordRun`, reports built on `output.save`. Independent of the above; could go first if a release needs a quick win.
6. **Sandbox worker pool (1 week):** `ScriptRunner` in `ExecServices`, pool on `worker_threads`, in-thread runner kept for the CLI. Then the same pool for import parsing and hashing.
7. **RPC contract manifest + `run-service.ts` (1 week):** generated contract, `rpcVersion`, typed `call`; the one run orchestrator used by backend, CLI and MCP.
8. **Barrel split + process policy (3 days):** subpath exports, `net/process.ts` as the only `child_process` importer, desktop-only modules out of the root barrel; size ratchets.
9. **Registry ratchets (ongoing, per release):** kind branches outside `kinds/`, protocol `case`s outside `protocols/`, renderer `kind-ui`.

Steps 1, 2, 5 and 8 are safe inside the current release rhythm; 3, 4 and 6 are the cloud foundation (Phase C0) and should be their own milestone.

## What is already good

- **One engine, three hosts** is real: `runTests`/`runCollection`, the AI task runner, the redactor, the production guard and the output registry are shared, and the layering is enforced by tests (`architecture.test.ts`, `import-graph.test.ts`: no cycle in core).
- **The renderer is already a pure RPC client**: no Node/Electron import, errors as plain envelopes, `saveOrDownload` with a browser fallback, visualisations on an isolated origin.
- **AsyncLocalStorage is already the per-call mechanism** for own-writes (`own-writes.ts`) and production consent (`production-guard.ts`): the `RequestContext` proposal extends what exists instead of inventing a pattern.
- **Bounded buffers everywhere the UI listens**: console 500, logs 500, MCP events 5,000, viz pages 30, Debugger exchanges capped, results index 4 files, history 20k / traces 50k pruned with their files, import previews 8, text cache 64 MB, own-writes 100k, dispatcher pools 32.
- **Streaming where it matters**: response bodies spooled to disk past the preview (96 MB test, flat heap), results to JSONL with a byte-offset index and 1,000-row pages, `output.save` streaming with progress and cancel, runner backpressure 2× concurrency, batched events (40/50/100 ms), terminal ack flow control.
- **Storage hygiene**: atomic writes (temp + fsync + rename), broken files kept as `.broken-<ts>`, `node:sqlite` with WAL + `busy_timeout` (safe for app + CLI side by side), indexed history columns (v2 migration), traces in one transaction per batch, trash with 30-day expiry, proposals with TTL.
- **The watcher design** (content fingerprints, own-write registry, sliced open walk, overflow rescan) is the right basis for multi-writer workspaces and git integration.
- **Nothing native stands in the way of a Linux container**: node-pty is desktop-only behind `host.terminal`, SQLite is built in, secrets go through an injected cipher, scripts run in WASM.
- **Scale is measured**: `core-scale.test.ts` (10k requests, 10k steps flat memory, 100k history rows, 96 MB body), `desktop-scale-handlers.test.ts` (10k-request tree, 5k test files), `backend-caches.test.ts`, the perf-large-workspace plan and `TESTPION_PROFILE`.
- **Server switches exist already**: `TESTPION_BLOCK_PRIVATE_NETWORKS`, `TESTPION_ALLOW_HOSTS`, `TESTPION_ALLOW_PROCESSES` (`policy.ts:28-36`), SSRF guard in the HTTP client (`client.ts:438`) — they need the enforcement gaps in §1 closed, not a redesign.
