## P0-1: the ghost row in the Collections sidebar

### What the owner sees (4 screenshots)

The workspace is TestPion Examples at density comfortable. `Live streams (SSE) › REST › GET Wikipedia edits, live` is the
active row, drawn highlighted and in the right place. A **second copy** of that row is also drawn: method badge and title, no
highlight, no count. That copy:

- sits over `Swagger Petstore (OpenAPI contract)` and MCP rows while a folder context menu is open (screenshot 1);
- sits in the empty area below the collapsed `Datasets` header when MCP servers, API definitions and Datasets are collapsed (screenshot 3);
- sits over `Context7 (library docs)` and `Cloudflare docs` when `MCP servers` is expanded (screenshot 4).

### What the code rules out

I read every component that draws into the sidebar:

- **No component draws a second copy of a row.** The code has no `cloneNode`, no `setDragImage`, no portal that renders a row,
  no reveal or flash overlay, and no "sticky active row" (grep over `src/`). WF-11 reveal only changes `open` state and
  calls `scrollToIndex` (`CollectionTree.tsx:516-548`, `VirtualList` in `ui.tsx:768-779`). The preview tab only changes the
  editor tabs. The SSE request is an ordinary `RequestRow` (`CollectionTree.tsx:938`). No "open editors" or "recent" pane
  exists in the explorer.
- **The VirtualList offset parent is correct.** With `scrollParent`, the list is `<div class="relative" style="height: rows × rowHeight">`
  (`ui.tsx:795`). Each row is `position:absolute; top:i*rowHeight` inside that div. The three library `Section`s come after
  the tree's wrapper (`Explorer.tsx:768-868`) in normal flow, so their position comes from the list's full height. A
  row drawn from the list can never land inside them unless its index is outside `0..rows.length`. `start` and `end` are
  clamped to `items.length` (`ui.tsx:783-784`).
- **Density and row height agree.** `rowHeight = 2 × settings.fontSize` (`CollectionTree.tsx:569`), then
  `scaledRow(…, useDensity())` (`ui.tsx:723`). Rows are `h-8` = 8 × `--spacing`. That is 2rem at comfortable and 1.72rem
  at compact, and `COMPACT_SCALE` = 0.86 = 0.215 / 0.25 (`styles.css:157`, `lib/density.ts:12`). The only mismatch is
  sub-pixel rounding (≤ 0.5 px), with no drift. The sticky `Section` headers (`Explorer.tsx:77`) stick only inside their
  own section box.
- **Duplicate React keys are not the cause in this workspace.** Keys are `req:<node id>`, folder keys are
  `folder:<node id>` and collection keys are `col:<id>` (`rowKey`, `CollectionTree.tsx:910`). These keys are not scoped
  by collection, so two collections that share node ids would collide. That can happen after a native TestPion import
  that keeps ids (`packages/core/src/import/importers.ts:475`). With colliding keys React leaves orphan rows at stale
  `top`s. But the example workspace has no duplicate ids: I checked every `examples/public-workspace/collections/*.json`,
  and `sse-wikimedia` exists only in `streams.json`. Duplicate keys therefore stay a latent bug to fix (below), not this
  glitch.

### The mechanism

The owner's own evidence decides it. **The ghost's position in the window never changes.** Between screenshots 3 and 4, only
the content under it changes: empty space when the sections are collapsed, MCP rows when `MCP servers` is expanded. An
element of the tree or the sidebar would move with the content, because its offset comes from the list, and the list does
not change when a section below it opens.

So the ghost is not a DOM row. It is the **HTML5 drag feedback image of that row**, left on screen after a drag that never
ended. Electron on Windows draws the drag image in a separate OS window during `DoDragDrop`. It shows an untouched
snapshot of the source element, taken at `dragstart` before the row became active. That is why the copy has the badge
and title but no highlight.

Every explorer row is `draggable`: requests (`CollectionTree.tsx:979`), folders (`:577`), saved items (`:73`) and
FolderList rows (`FolderList.tsx:132`). Three code paths in this tree can leave a drag without a `dragend` on Windows:

1. **The source row unmounts during the drag.**
   - `dragstart` calls `setDrag({c, n})` synchronously (`CollectionTree.tsx:288`), so the tree re-renders inside the
     handler.
   - A drag that auto-scrolls the sidebar, or one that changes `rows`, can take the source row out of the drawn window.
     That happens on a `data.changed` reload, on the reveal effect when the drag opens the request (dropping a request on
     the editor or tab strip opens it), and with more than 300 rows when `DRAW_ALL` stops applying. `VirtualList` then
     unmounts the source row.
   - Chromium sends `dragend` to the detached node, so React never sees it: `drag` and `dropAt` stay set. On Windows the
     OLE drag image can stay painted until the next drag.
2. **A drop target opens UI synchronously inside `drop`**, for example a prompt or dialog. A drop on the flow canvas or
   the tab strip can open an editor, which runs the reveal scroll. The drag loop is still running when the window
   repaints.
3. **A right-click or a menu opens while the drag loop is running.** This matches screenshot 1, where the folder context
   menu was open. Radix moves focus and listens for pointer events, and the context menu is a second input loop.

In all three cases the row the user dragged becomes the active row. A drop on the tab strip or canvas opens it, or a
click finishes the gesture. That is why the ghost always matches the selected row.

### Repro recipe (deterministic; run on the installed app with a copy of the profile, per `repro-installed-app.md`)

1. Open the TestPion Examples workspace at density comfortable. Expand `Live streams (SSE)`, then `REST`.
2. Press on `GET Wikipedia edits, live`, drag about 40 px, and drop it on the editor tab strip. That opens the request:
   it becomes active, the reveal runs, and the tree re-renders during the drag.
3. Variant A: drag the row and hold it near the bottom edge of the sidebar until the sidebar auto-scrolls, so the
   source row leaves the drawn window. Then release over the MCP section.
4. Variant B: during the drag, right-click a folder in `MCP servers` (screenshot 1).
5. Expected bug: a translucent `GET Wikipedia edits, live` stays drawn at one screen position. Expand or collapse
   `MCP servers`: the ghost stays put while the rows move under it.
6. Discriminators. These confirm or kill the hypothesis in 2 minutes.
   - In DevTools, run `document.elementsFromPoint(x, y)` at the ghost's position. A drag image or compositor ghost
     returns no `[data-node-id]` element.
   - Run `document.querySelectorAll('[data-node-id="sse-wikimedia"]').length`. It must return `1`.
   - Take a CDP `Page.captureScreenshot`. An OS drag image is **absent** from it but present in a desktop screenshot.
   - Move the window. An OS drag image stays where it is on screen. A compositor ghost moves with the window.
   - If `querySelectorAll` returns `2`, the cause is the duplicate-key path. Apply fix 4 first.

### Fix (in `lib/drag-ref.ts`, the one helper every source already calls)

1. **Use one explicit drag image for every source.** `setDragRefs(e, refs, label)` builds a small chip ("GET Wikipedia
   edits, live" or "3 items") in an off-screen container. It calls `dt.setDragImage(chip, 8, 8)` and removes the chip on
   the next frame. The OS then never snapshots a live row, and the image is the same in every tree (uniform UI).
2. **Keep the source row mounted.** `VirtualList` gets `keepIndex?: number`, and `CollectionTree` passes the dragged
   row's index. The row stays drawn, absolutely positioned, while it is outside the window, so `dragend` always reaches
   React. Also defer `setDrag` to `requestAnimationFrame`, so the source row does not re-render inside `dragstart`.
3. **Add a global safety net.** A `useDragSession()` hook in `drag-ref.ts` sets window listeners while a drag is active:
   `dragend`, `drop`, `pointerdown`, `blur` and `keydown Escape`. Each clears every tree's `drag` and `dropAt` and any
   drop highlight. Tree code stops relying on the source element's `onDragEnd`.
4. **Fix the latent duplicate-key bug.** Scope the keys:
   `rowKey = r.t + ':' + (r.c?.id ?? '') + ':' + r.key` (`CollectionTree.tsx:910`). Add a dev-only assert in
   `VirtualList` that `console.error`s once on a duplicate key. On import and `col.save`, give fresh ids to node ids that
   already exist in another collection (`importers.ts:475`, core).
5. **Never open UI synchronously in a drop handler.** Drop targets (tab strip, flow canvas, collection drop) run their
   action in `setTimeout(…, 0)`, the same pattern as `runSelected` in `ui.tsx:577`.
6. Add `contain: layout paint` on the `VirtualList` container. This is defence in depth: no row can paint outside the
   list's box. It costs nothing because rows already fit inside.

## 2. The model

### Anatomy (one function, one group order everywhere)

`MENU_GROUPS` becomes the enforced order (it replaces today's order in `lib/vocabulary.ts:30`):

```
create · open · tree · run · share · tools · edit · danger
```

| Group | Items (LABEL keys) | Applies to |
|---|---|---|
| **create** | New <kind> (one item per kind the container holds), New folder | every container; a section header |
| **open** | Open, Open in new tab, Reveal in sidebar (outside the sidebar only), History in git…, Reveal file / Show in folder | leaves; file-backed items |
| **tree** | Expand all, Collapse all (scoped to the subtree; on a section header, the whole section) | **every container, always**: collection, folder, category, saved-item folder, library folder, section header, test folder |
| **run** | Run / Run collection / Run folder, kind actions (Connect, Lint, Preview …) | kind-specific |
| **share** | Copy link, Copy as … (cURL, grpcurl, MCP config, path), Export… | every item with an ItemRef (Copy link is generated from `toItemRef`) |
| **tools** | Monitor on a schedule…, Run in CI…, Create test file…, Generate integration flow with AI…, Settings…, Convert scripts… | generated from the node's capabilities |
| **edit** | Rename, Duplicate, Move to…, Add to / Remove from favorites | every node with ops |
| **danger** | Delete… / Delete folder… (always `deleteWithUndo`) | every node with ops |

### Rules

1. One `buildNodeMenu(node, ctx)` builds **every** tree and list node menu: each tree row, each FolderList row, each
   Explorer row, folder and section header, the Tests tree, and the History, Traces, Git and Environments rows.
2. Kind-specific items come from a **registry** (`NODE_KINDS`). Shared groups come from **capabilities**, so a new kind gets
   tree, share, tools, edit and danger for free. `kind.capabilities` lists which of these the kind supports: `container`,
   `runnable`, `monitorable`, `ciRunnable`, `testable`, `flowable`, `linkable`, `renamable`, `duplicable`, `movable`,
   `deletable` and `favorite`.
3. An item that doesn't apply is **omitted**. An item that applies but can't run now is **disabled with `title` (the
   reason)**. Example: "Run in CI…" on an unsaved request shows "Save the request first".
4. Separators sit between non-empty groups only. Labels come only from `LABEL`, and `RETIRED_LABELS` stay banned.
5. The menu is built only while it is open (lazy). A closed row holds no `MenuItem[]`.

## 3. Behaviour parity

- **Expand all and Collapse all, built once.**
  - New `lib/tree-state.ts`, with `useTreeOpen(scope)` on top of `usePersisted`. That store is already
    workspace-scoped through `scopedKey` (`lib/sticky.ts:14`).
  - Keys are `<scope>:<nodeKey>`. Today's separate stores move into it: `aps.tree.open` (CollectionTree),
    `aps.explorer.sections.v2` (Explorer) and `aps.folders.<id>` (FolderList). The old values are read once to migrate
    them.
  - `setSubtree(scope, rootKey, open, descendantKeys)` is the one implementation. CollectionTree's `setSubtree`
    (`:420`) moves there.
  - The header "Collapse all" button (`Explorer.tsx:732`) calls the same function for every scope.
- **Keys**, in `treeKeys` (`TreeParts.tsx:309`), for every tree:
  - ← and → already work, and Home and End too;
  - `*` expands the focused container's subtree;
  - Shift+F10 and the ContextMenu key open the focused row's menu;
  - F2 renames and Delete deletes through `menuKeys`, using the built menu, so the keys always match the menu;
  - Enter opens; typeahead (letters jump to the next row whose name starts with them).
  - Rows get `data-menu-id` so `treeKeys` can open the row's menu without per-view code.
- **Multi-select** (phase 4).
  - Ctrl or Shift+click selects in the explorer, FolderList and the Tests tree, through a `useTreeSelection(scope)`
    shared hook.
  - The menu then comes from `buildNodeMenu({ kind: 'selection', nodes })`: Delete N items… (one Undo), Move N items
    to…, Copy N links, Create test file from N…, Create flow from N…. Debugger already does this, at
    `DebuggerGrid.tsx:310`.
- **Drag and drop.**
  - Every draggable row calls `setDragRefs`, including FolderList, which today uses a private mime (`FolderList.tsx:133`).
  - Every folder row is a drop target for its kind, through `useDropTarget(kind, onDrop)`.
  - The drag image and the cleanup come from P0-1.
- **Delete is always `deleteWithUndo`.** That includes the MCP server, which today uses a confirm dialog
  (`Explorer.tsx:559`), and the Tests folder.
- **Toasts after Create / Duplicate / Move** carry `{ ref }`, so they show an Open action, the same way
  `CollectionTree.tsx:219` and `:346` already do.

### Performance

- Menus are built only on open: `Menu` already mounts lazily (`ui.tsx:498`), and the items become a thunk.
- No row holds a `MenuItem[]` while closed. Today `FolderList.tsx:164` and `Explorer.tsx:801`/`822` build menus on
  every render; that goes away.
- `buildNodeMenu` must take under 1 ms. Budget: the 9,000-row `perf-large-workspace` plan stays within today's
  numbers, and opening a menu on a 9,000-row tree stays under 33 ms, the two-frame floor (`ui-perf-profiling.md`).
- `TreeRowShell` stays `memo`'d with primitive props. Callbacks go through a ref context, as `RequestRow` does today
  (`CollectionTree.tsx:552`).

  `menu` / `menuitem`. Disabled items get `aria-disabled` and `title` for the reason.
- Focus returns to the row after the menu closes. Rename and Delete already go back through `focusRow`.
- Typeahead works in the tree; Radix already handles typeahead inside the menu.
- The ⋯ button is named "More actions for <name>" everywhere (already true).

### Risks

- Changing the group order moves items users know: Run moves after Expand all. Mitigation: the item labels stay the
  same, and What's new names the change.
- Tree-state key migration can lose remembered folder states. Mitigation: read the old keys once, and test the
  migration.
- MCP server delete with Undo means restoring the server's config. `editServers` with `putBack` covers it, but a
  connected server must reconnect on Undo.
- The drag-image fix depends on Windows OLE behaviour. Verify it on the installed app (`install-and-verify` skill), not
  only in dev.
- More items per menu means longer menus. Keep each menu at 18 items or fewer and fold the Copy-as variants into a
  `Copy as ▸` submenu. That is a change for the request menu (6 items today).
