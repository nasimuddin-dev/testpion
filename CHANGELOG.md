# Changelog

## Unreleased

### Core engine: faster, bounded, paged

- **Faster runs.** A run of HTTP tests spends about 13% less CPU per test; a run of 1,000 steps × 100 iterations takes 0.67 s instead of 1.3 s (ids come from a pool of random bytes, secret-key rules are remembered per name, the list of check types is cached, a JSON-path check evaluates its path once). Registering a thousand secrets takes 0.2 ms instead of 88 ms. The history of one test over 60 runs of 5,000 results is 2 to 3 times faster; test generation from a 4,000-operation OpenAPI document takes 1.6 s instead of 6.9 s, and its lint no longer scans the whole document for every problem.
- **Long lists come in pages** (`limit`, `cursor`, `truncated`, `total`): a run's results (`runs.results`: at most 1,000 a page), the flaky tests (new `flakyTestsPage`), and a search (`offset` in the query, `truncated` and `nextOffset` in the answer).
- **A collection of more than 1,000 requests runs to the end** (the guard against a `setNextRequest` loop counted requests per iteration with a fixed limit of 1,000; it is now four times the collection's size, at least 1,000).
- **Scans remember files.** The exposed flows (MCP tools list), the webhook flows and the spec gap analysis read a test file again only when its size or time changed; connection pools, OAuth tokens and test-set verifier state are bounded.

### RAG follow-ups: judges, test sets, capture, calibration, authoring

- **138 metrics** (was 134). `answer-regex`, `answer-length` and `answer-json-schema` (DeepEval's JsonCorrectness) score the shape of an answer 1 or 0 with no model; `judge-cost` is what judging the other metrics of the sample cost, in dollars (lower is better, `max` gates it). `negative-rejection` takes `mode: judge` for a refusal the pattern does not know. Ragas' one `noise_sensitivity` takes `mode: relevant | irrelevant`. A jury now also votes on the claim-level metrics, claim by claim.
- **A `dag` kind of custom metric** (a decision tree in `metrics/<id>.yaml`) with a **Decision tree editor** in the metric editor: the questions in the order they are asked, where each answer leads (a question or a score and why), add, remove and rename nodes; every change is written back into the YAML. The tree is checked like the built-in `dag` metric's, and the catalogue row says the most judge calls a sample can cost.
- **Test sets get a voice and a meaning check.** Personas (`--persona`) and styles (`--style`: formal, casual, terse, verbose, typos, non-native) go round the slots; each record keeps them in its tags. `--dedupe embedding` (`--embedder`) also finds repeated questions by meaning, redacted and with the words as the fallback that says so; the estimate counts the embeddings.
- **Captured datasets: reference answers and more protocols.** *Draft reference answers…* (`testpion rag draft-references`, MCP `rag_draft_references`, the AI task `rag-draft-references`) drafts a reference for each record that has none **from the passages it retrieved, not from the system's answer**, checks every draft against them and offers one proposal; accepting replaces the record by id (one Undo). Capture reads gRPC and MCP calls of History (questions only: History keeps no response) and a WebSocket message log (`--messages`).
- **Calibration**: a jury's members have their own rows (kappa, accuracy, TPR, TNR against your labels), safety and conversation judges calibrate like any other (a label belongs to the whole transcript, a disagreement shows the last turns), the report downloads as Markdown or JSON (the new output surface `rag.calibration`; `rag calibrate --out`), and **Make an example of this** turns a disagreement into an example of a custom metric (`rag metric example`, MCP `rag_make_metric_example`).
- **Authoring**: the gates of a drafted evaluation are a field of the saved evaluation (a **Gates** field in the editor; `rag run`, a monitor of the evaluation and CI use them, a `--min` for the same metric wins), and `--slice-file` also writes the slice it runs to `datasets/<name>.jsonl`.
- **Conversations**: **Conversation** is a field of the dataset column mapper (the question becomes the last user message), and a server-session target can keep its session in a **cookie** (`conversation.cookies`): the cookies each answer sets go with the next turn of the same conversation only, never shared and never stored.
- **The bundle carries custom metrics.** Export… and Import… handle `metrics/*.yaml` (`metric` is a bundle kind; a script or judge metric is listed in the import's Review). Under the hood: `eval/rag/custom/file.ts` and `metric-matrix.ts` use the shared `isRecord` and `percentile`.
### RAG R4: generate, capture, calibrate, author, watch

- **Test sets from documents.** AI Lab ▸ RAG ▸ Data ▸ *Generate a test set from documents…*: documents (md, txt, html, https pages) are chunked deterministically, the AI task `rag-generate-testset` writes single-hop, multi-hop, abstract, unanswerable and adversarial questions with reference answers and chunk ids, and every sample is verified (lexical and judge entailment support, a keyword-retrieval check that unanswerable questions are unanswerable, duplicates) and reviewed in the shared proposal review before it is added to `datasets/<name>.jsonl`. Estimate, caps and *What will be sent* come first; document URLs are https only, public addresses only, same-host redirects, 2 MB. `testpion rag generate-dataset`, MCP `rag_generate_testset`.
- **Datasets from real calls.** *Create dataset from captured calls…* (History, the Debugger, AI Lab ▸ RAG ▸ Data): the question is read from the request where the RAG target writes it, the answer and contexts with its mapping; secrets and personal data are masked before anything is written; dedupe, seeded sampling, preview. `testpion rag capture`, MCP `rag_capture_dataset`.
- **Judge calibration.** Pass/Fail labels on a result's metrics (the matrix drill-down) stored in `labels/*.json` with provenance; *Calibrate judge* shows Cohen's kappa, accuracy, TPR/TNR, the confusion matrix, bootstrap intervals, the numbers per judge model, disagreements, and the pass mark that agrees most (applied to the evaluation or the metric file). `testpion rag label|calibrate` (`--min-kappa` gate), MCP `rag_label`, `rag_calibrate`.
- **Draft an evaluation with AI** (AI-11). `rag-author-evaluation` proposes a complete RAG evaluation (metrics with pass marks and reasons, judge options, gates); metrics that cannot run on the data are dropped with a note, and a dry run on a few samples (free metrics for real, judged prompts counted, nothing sent) is the badge on the proposal. `testpion rag author`, MCP `rag_author_evaluation`.
- **Trends, nightly runs, CI.** `testpion rag trend` / MCP `rag_trend` / a Trend view with the shared chart output control (a change of judge or prompt is marked, not read as a regression); monitors get a rotating nightly sample, a per-run budget and a regression gate against a baseline, with the alert carrying the metric table; the CI dialog and `ci` get a scheduled nightly RAG workflow and a regression section in the PR comment. The metric editor has *Save as…*; the redactor now masks a phone number that ends a sentence.
- New proposal item kinds `dataset-row` and `evaluation`; AI tasks that read a folder or a target (`prepareContext`) run without a workspace item.
### RAG: a SQL metric can only read the databases its saved definition names; faster matrix, estimate and judge path

- **A SQL metric can only read the databases its saved definition names.** `datacompy-score` and `sql-equivalence` read a SQLite file only inside the workspace (and fail closed where no workspace folder is known), never a `database` an agent or a request passes in its options (`rag_try_metric` and the Try dialog take an `evaluation` instead and use its database), and a PostgreSQL or MySQL connection that a workspace file names (`url`, or `connectionEnv` pointing at any environment variable, even marked `readOnly: true`) is n/a until you allow that target on this computer: `testpion rag trust-db "<target>"` (the n/a message prints the exact line). The decision is kept in the app's data folder, not in the workspace, names the host and database (a changed variable asks again), and no agent can make it.
- **The SQL checker reads each dialect the way its server does.** A MySQL `--x`, a `#` comment, `/*! … */` and `/*M! … */` comments, a backslash outside a string, an unusual space or control character and a quoted function name (`"pg_read_file"(…)`) are refused instead of stripped; a PostgreSQL line comment ends at a carriage return; a number runs into no keyword. A hostile-input list per dialect (SQLite, PostgreSQL, MySQL) is a test.
- **A SQLite query cannot take the computer's memory.** `x||x` in a recursive query, `printf('%1000000000c')` and `group_concat` stop at SQLite's own size limits (16 MB a value, 30 compound terms, 32 function arguments), the heap is capped, and a query that makes the process grow by 1 GB is killed.
- **The RAG MCP tools that send requests or spend judge tokens ask first.** `rag_run`, `rag_rescore`, `rag_probe`, a real `rag_try_metric` (a dry run that asks no target needs none), `rag_validate_metric` with `run_examples`, and `rag_import_dataset` with `save_as` need `confirm: true` (or a yes to the client's question).
- **The metrics matrix of a 5,000-sample, 84-metric run opens in 0.1 to 0.2 s instead of 3 s and pages, sorts, filters and pass-mark edits take about 20 ms** instead of a full rebuild each: the built matrix is kept per run, the 95% intervals are asked for the columns on screen (once each), only the rows on screen are drawn, and typing a pass mark no longer redraws the table.
- **The exact estimate of a big run keeps counts, not prompts** (9 MB for 1,200 samples became 0.01 MB; 300 to 800 MB at 5,000 samples × 10 metrics), a judged sample builds its prompt once per model call instead of twice, the judge cache is indexed by time, custom metric files are read once while the `metrics/` folder is unchanged (the lists reload only when a metric file changed), and a search over trace files lets the app breathe between the reads.

### RAG R3: conversations, agents, safety, pictures, decision trees; every catalogue row runs

- **134 metrics** (was 84), and a test that **runs every one of them** on a fixture sample (judged metrics through the offline mock judge, the classifier a local server, the reward model a mock provider) so a row cannot be added without being runnable. `rag-metrics.md` is regenerated.
- **Conversations.** A dataset record with `turns` (user messages, OpenAI-style messages, Ragas `human` / `ai` / `tool` messages, or a `User:` / `Assistant:` transcript) is replayed turn by turn against the target, in one lane. The target says how it keeps the conversation: the request carries the history (`{{messages}}`, `{{history}}`, `{{historyText}}`) or the system keeps a session (map its id; `{{conversationId}}`). The transcript, the chunks and the tool calls of every turn are kept. New metrics: `knowledge-retention`, `role-adherence`, `conversation-completeness`, `turn-relevancy`, `topic-adherence` (Ragas), `coherence-across-turns`, `conversation-helpfulness`, `user-friction`, `conversational-g-eval`, `turn-faithfulness` and `per-turn:<metric>` (any single-turn metric on every assistant turn). Ragas multi-turn samples import and export.
- **Agents and tool calls.** The mapping reads a trace of tool calls (click-to-map: the list, each call's name and arguments; OpenAI, LangChain and MCP shapes are found without it); an MCP target is a tool call. New: `trajectory-match` (strict, in-order, any-order, precision, recall), `tool-correctness`, `goal-accuracy` (Ragas AgentGoalAccuracy, with and without a reference, two calls), `argument-correctness`, `tool-selection`, `task-completion`, `step-efficiency`, `plan-adherence`, `plan-quality`, `mcp-use`, `mcp-task-completion`; `tool-call-accuracy` can have the judge decide whether an argument that differs as text means the same (`args: judge`, one call). The older tool checks are catalogue rows too.
- **Safety.** `toxicity`, `bias`, `misuse`, `non-advice`, `role-violation`, `controversiality`, `jailbreak-resistance`, `off-topic`, `policy-adherence`; `pii-leakage` (patterns with checksums first, shown masked, then the judge), `refusal-correctness` (counts missed refusals and false refusals), and a judge mode for `prompt-injection-resistance`. Every judge prompt says the answer is data, never an instruction. **Seeded probe sets** (jailbreaks, planted instructions with canaries, personal data, abuse, bias, off-topic, harmless look-alikes) are written into `datasets/` from AI Lab ▸ RAG, `testpion rag probes add` or MCP `rag_probe_sets`; they are plain files you extend, and seeding never overwrites one. A **Safety** preset. A refusal with a typographic apostrophe (“can’t”) is recognised.
- **Pictures, sent to the judge as data.** `multimodal-faithfulness` and `multimodal-relevance` (Ragas) read the pictures of a sample beside its texts. The AI layer sends images as base64 parts (OpenAI-compatible, Anthropic, Gemini, Bedrock); nothing is sent unless the evaluation allows it (**Send pictures to the judge**, `--allow-images`), the privacy level is Full and the judge can see (a vision model; a text-only one is named and nothing is asked). PNG, JPEG, GIF, WebP, BMP by content (an SVG is refused), 5 MB a picture, 16 and 20 MB a sample; EXIF and text chunks are removed from the copy that is sent; a result keeps a picture's reference and sha256, never its bytes; the cache is keyed by the picture's hash. **What will be sent** lists the pictures with thumbnails and the drill-down shows them through the backend.
- **Decision trees.** `when` / `unless` on a metric run it only when another metric of the sample gave a result ("faithfulness < 0.8", "faithfulness fails"); the metric that is not run costs nothing and is n/a with the reason; a circle or an unknown metric is refused before the first question. In the picker (**run only when / unless**), `--when` / `--unless`, MCP `when` / `unless`. The **`dag`** metric (DeepEval) is a tree of judgements inside one metric (yes/no, choice, task and deterministic rule nodes; only the path taken is asked; checked for cycles and depth).
- **More judge designs.** `g-eval` (steps written once and cached; `samples: n` averages ratings, because the AI layer has no token probabilities), `pairwise` (blinded, both orders, win rate against `baseline_answer`), `summarization` (DeepEval and Ragas), `faithfulness-hhem` (claims by the judge, entailment by a classifier you serve, e.g. Vectara HHEM), `reward-score` (Nemotron reward models on an OpenAI-compatible endpoint). The classifier and the reward model obey privacy level, redaction, Local only and the ledger like any judge.
- **SQL production guard.** A database marked `production: true` is asked about once before the generated SQL touches it: the same question and consent as a request to a production environment (the app asks, the CLI takes `--allow-production`).
- **The picker** edits text options (a role, topics, rules, a criterion, a tree as JSON), marks the required ones, and has the decision-tree control. The Try dialog takes pictures and the other fields of a record (a conversation, tool calls, `should_refuse`).
- **Tests.** Golden mock-judge cases for every worked example (Ragas' topic adherence 0.8, the Tesla multimodal pair, goal accuracy in two calls, G-Eval 0.75 / 0.625, DAG paths, pairwise orders, summarization 0.8, HHEM 0.75, reward 0.8), a conversation run against local servers (stateless history, server session, tool calls, per-turn scores, routes, probe sets, a picture kept by hash only), image/EXIF/limit/consent/redaction tests, and the 5,000 × 40 matrix perf budget (`rag-matrix-perf`).
### Refactor and cleanup (B-41)
- **Workspace export is a bundle now.** The workspace switcher's Export…, the Export dialog's *The whole workspace* and `testpion workspace export` write `<name>.testpion.zip` (a small workspace of text only: `.testpion.json`), the same bundle `testpion export --all` writes: it opens as a new workspace with Import in the workspace switcher, or merges into an open one with a preview, conflict choices and Undo. The workspace's own variables (the Globals) are not part of a bundle; the export says so. The old workspace export (`workspace.export`, `storage/workspace-bundle.ts`) is deprecated in favour of bundles and stays for two more releases.
### Faster: Git changes, bundles, imports and the command line
- **Git changes by item** read the 'before' of every changed file through two `git` processes, not one or more per file (300 modified files: 311 processes and 28 s before, 2 and about 1 s now), remember the rows of files that did not change since the last refresh, and give the app a turn while thousands of new files are read. The status bar, the explorer and the environments list no longer render again when a refresh finds nothing new.
- **Bundles and imports of big libraries.** Exporting or previewing a bundle of 2,500 saved items took 20 to 26 s (the library file was read and parsed once per item); it takes under half a second. "Keep both" for 2,500 conflicts applies in 1.5 s (it was 35 s) and Undo of it in 0.4 s (it was over two minutes). Import journals of bundles keep the newest 30.
- **Importing a folder of files** into a workspace that already holds 10,000 requests reads the workspace's collections once, not three times per file (100 files: 32 s to 5 s; the preview 15 s to 1 s). The list of earlier imports no longer reads their receipts, identical scripts of a collection are converted once, and saving a collection with thousands of requests orders its keys in one pass.
- **`testpion --version` and `testpion --help`** answer from an index written at build time, without loading the command line.

### Security hardening

- **A Fiddler SAZ file is opened by the hardened zip reader.** Importing a `.saz` (Debugger) used a zip reader of its own that checked nothing: a zip bomb, an entry count in the hundreds of thousands, a name like `../x` or a damaged entry now stop the import with a message, the same limits as a bundle's.
- **MCP `save_output` only writes under `exports/`.** `save_to` is an allow-list now: a new file under `exports/` or `.local/exports/`, never over a file, never in a hidden folder (`.husky/`, `.vscode/`) or as a program file, and it asks for confirmation (`confirm: true`). `export_bundle` follows the same rule (a numbered name instead of overwriting the default file).
- **More MCP tools ask first**: `export_traces` (sends traces to an endpoint), `security_tests_run`, `import_definition` (when it updates) and `undo_definition_import`.
- **Imported AI providers never bring secret references.** A bundle's provider or remote MCP server is imported without its `{{$secret…}}` / `{{$env…}}` key, headers and variables (you enter the key yourself) and with only the fields TestPion knows; Review says where it sends things and warns when Replace would move one of yours to another address.
- **Importing from a link follows the network policy.** The link and every redirect hop are checked (https only where private networks are blocked, at most 5 hops); IPv6 spellings of private addresses (`::ffff:7f00:1`, NAT64, 6to4, IPv4-compatible) are recognised.
- **The pre-commit hook no longer expands the workspace folder name** (`$(…)`, backticks, quotes, line breaks stay text).
- **Git paths**: the `.git` folder is refused in any spelling (`.GIT`, `GIT~1`, trailing dots) and at any depth; a file name with a line break cannot be tracked by LFS or by reference; the secret scan's allowlist fingerprints are salted and slow (older allowlists keep working).
- **Import limits**: at most 8 import previews are kept (30 minutes), uploads are measured before they are decoded, zip bombs are caught for entries of any size and as a whole, and a bundle holds at most 512 MB once unpacked.
- **RPC parameter checks** for the RAG, bundle and large-file calls, and a test that fails when a new call has none.

### RAG R2: every judged metric, your own metrics, SQL, Ragas parity

- **84 metrics** (was 30). New judged metrics on the judge service (cache, ledger, budget, jury and swap as before): `context-precision` and `context-recall` with the judged variants, `context-entity-recall`, `factual-correctness`, `answer-correctness`, `response-groundedness`, `hallucination`, `correctness`, `completeness`, `factuality`, `citation-accuracy`, `negative-rejection`, the claim-level family (`claim-faithfulness`, `claim-recall`, `claim-hallucination`, `noise-sensitivity-relevant` / `-irrelevant` …; one claim pass is shared between them), and the judge templates (pass/fail, simple criteria, rubric, instance rubric, checklist, prompt alignment, coherence, conciseness, helpfulness, comprehensiveness, harmfulness, maliciousness). Without a judge in a RAG target run they are n/a, never a guessed score.
- **Free metrics added**: `hole@k`, graded `ndcg@k` (from `relevance` in the record), `bleu`, `chrf`, `numeric-diff`, `json-diff`, `label-f1`, `quoted-spans`, semantic set metrics, `context-size`, `context-usage`, `error-rate`, `throughput`, `retrieval-score-stats`, `prompt-injection-resistance`, `tool-call-f1`, `tool-call-accuracy`. - **Changed meaning, said at the place it matters.** `hallucination` is now DeepEval's metric: the share of unsupported claims, **lower is better**. It used to be another name of `faithfulness`; a test file that uses it gets an info line saying so, and `faithfulness` is the higher-is-better metric. `answer-correctness` reads claims both ways; the older sentence-overlap behaviour remains for a test file without a judge. In a RAG target run `context-precision`, `context-recall` and `context-entity-recall` are strict (no judge, no score); a test with contexts written in the file keeps the heuristic.
- **Custom metrics.** `metrics/<id>.yaml`: a judge criterion, a checklist, deterministic rules, a formula over other metrics (its own expression language, no eval), an embedding set or a sandboxed script, each with examples that act as the metric's tests. AI Lab ▸ RAG ▸ Metrics edits them (live check, Run examples, Try on a sample, usage before delete), **Draft with AI** writes one as a reviewed proposal (task `rag-draft-metric`, its examples run before it is shown), the metric picker lists them, `testpion rag metric new|list|validate|export|import`, MCP `rag_list_custom_metrics`, `rag_validate_metric`, `rag_save_custom_metric`. The `metric` item kind is live (a git file; copied by `rag metric export`/`import`, not yet carried by the workspace bundle). Documented in docs/ai-testing/custom-metrics.md.
- **SQL metrics and a read-only executor.** `datacompy-score` (what the generated query returns against the reference query's result) and `sql-equivalence` (a judge's opinion). The executor accepts one `SELECT` only (no `PRAGMA`, `ATTACH`, writes, extensions or stacked statements, in both readings of a backslash), caps rows and time, opens SQLite read-only on a worker thread that is terminated on timeout, and runs PostgreSQL and MySQL in a read-only transaction with a statement timeout (the source must be marked `readOnly: true`). Hostile-input tests cover it.
- **Ragas parity.** `--compat ragas` (and `compat: ragas` in a saved evaluation) reads Ragas metric names with Ragas options; `rag export --names ragas` and `rag matrix --names ragas` name the columns as Ragas does; `rag matrix --ragas-result file` brings the scores of a Ragas result table in beside yours as external columns. `--repeat-target n` calls the RAG system n times per question and scores the mean with the spread.
- **The results, more ways to read them.** The matrix exports (CSV, JSON, HTML; `rag.matrix` output surface, `testpion rag matrix`), a **By tag** view, **Charts**, **Compare** against another run, a **Runs × metrics** pivot, **Score again…** from the matrix, **Free metrics first** in the estimate dialog, the raw call to the RAG system in a sample's drill-down, and **Explain this sample** (AI task `rag-explain-sample`, reads only that sample, proposes nothing).
- **Monitors and CI.** The monitor editor runs a saved RAG evaluation (gates, a number of questions, a share of the samples that are judged, a daily judge budget). The Run in CI dialog has RAG evaluations with gates, a preset, a baseline, a judge budget, metric names, calls per question and, for GitHub, a pull-request comment with the metrics table (`--markdown`).
- **Housekeeping.** The flow-format and checks references name the new check types (token budgets raised for that and nothing else). The SQL metrics reach the executor through a hand-over (`eval/rag/sql-host.ts`), so the metric engine still imports nothing from the runner at run time.

### Import compatibility, release B: every other tool, updates, and the way back out

- **Thunder Client, Yaak, HTTPie and Apidog import.** Collections and environments of Thunder Client (GUI tests become assertions or test code, `tc.*` scripts and `{{#guid}}`-style generators are converted), Yaak (the workspace export or a git-sync folder; `${[ var ]}` templates, gRPC and WebSocket requests), HTTPie for Desktop and Apidog (endpoints become requests under `{{baseUrl}}`, bodies from examples or schemas, responses as examples). Each is one module of the import pipeline with fixtures written from the tools' public documentation.
- **Postman v1, v3 and Native Git.** The first export format (`requests` + `order`), the file-based v3 format of Postman's Git integration (a folder of `*.request.yaml` files and `.resources/definition.yaml`, read from a folder, a ZIP or a link) and the Native Git layout (collections, environments and globals; the cloud id in `.postman/resources.yaml` identifies the collection for updates). **Postman globals become the workspace's globals** (secrets to the secret store); without a globals store (the CLI) they come over as an environment.
- **Importing again updates.** An import of a source imported before shows what it would do to the collection it made, item by item: **replace** what the source changed, **new** what it added, **skip** what is unchanged or what you edited here too (a conflict stays yours unless you choose Replace). The match is the tool's own id of the request or folder where there is one, else its path. The collection keeps its ids, an update is one undo step, an environment of the same name gets only its missing variables. `testpion import` updates by default (`--new-copy` adds a copy, `--update-decisions file` overrides single items), MCP `import_definition` takes `update` and `decisions`.
- **Simple tests become assertions** (a status, a response time, a header, a body text, a field of the JSON; about fifteen exact shapes, in `pm.*` or `tp.*`): the report counts them, **Lift N simple tests into assertions** (`--lift-tests`, MCP `lift_tests`) moves them into the request's Tests tab and keeps the rest of the script.
- **Script conversion for more tools.** Hoppscotch `pw.*` / `hopp.*` (Jest-style matchers become chai) and Thunder `tc.*` are converted to `tp.*`; Bruno's `req`, `res` and `res('path')` now become `tp.request` / `tp.response` too, `bru.sendRequest` is an adapter over `tp.sendRequest`, `bru.cookies.jar()` is `tp.cookies.jar()` (with Bruno's method names), `req.setTimeout` / `setMaxRedirects` with a number move to the request's settings, `bru.getProcessEnv` names a value to enter, and `pm.state` is `tp.state` (kept as globals named `state.<key>`). `pm.datasets` and `pm.mock` have no equivalent and say what to use instead. `testpion scripts convert --from bruno|insomnia|thunder|hoppscotch|postman` (`--file` for one script, `--report`) and MCP `convert_scripts` / `convert_script_code`.

### Explain and fix failures with AI

Your model sees each group's examples with the evidence — the request, the response, the failed check as the test writes it, and what changed since the same test last passed — and answers with **causes** (one cause may explain many groups), each with its evidence, a confidence and a fix. ([Explain and fix failures](/ai-testing/ai-features#explain-and-fix-failures-triage))
- **Every fix is proven before you see it**: a changed check must pass on the failing response, must not pass on any response (an empty body or an error page), and is run on the last passing response too (*it follows an API change* when it would have failed there); an edited test file must lint and an edited script pass in the sandbox; a variable fix must be one the failing steps missed and never a secret. When the test is right and the API regressed, the fix is a **bug report** to copy, with what changed since the last pass.

- **You decide**: nothing changes before **Apply selected fixes**; then **Rerun the affected tests** and **Undo**.
- **Privacy**: failure bodies are masked like every AI context, and *Metadata only* sends the method and URL (query values as `…`), statuses, check types and names, the checks as the test writes them, header names, the shape of bodies (field names and types, a text as `string (N chars)`) and which headers changed since the last pass; the body's changes since then go as shapes only (how many; each change's path and kind as `string (N chars)`, not which fields) — no body values, no failure messages. *Names only* sends the URL's path, and expected values and most numbers as their type. ### Why is this flaky?
- **Why is this flaky?** on a flaky test (the Problems panel, a result's **History** tab): TestPion reads its results across runs — pass rate, flips, retries, the environments and statuses of its failures, its time when it passes and when it fails — and your model names the pattern (timing, ordering, shared state, a time-dependent value, an external dependency, a rate limit, a data collision) with evidence and a fix that makes it stable without hiding a failure: a wait (`until:`), a stable check, isolated data; a retry only as a last resort, always flagged. Skipping or quarantining the test is never offered. ([Why is this flaky?](/ai-testing/ai-features#why-is-this-flaky))
- **The pattern starts from a signature TestPion computes**: how the failing responses differ from passing ones (*$.status: "done" when it passes, "running" when it fails*) and the pattern it points to (an intermediate state → timing and a wait; 429 → rate limit; 409 → data collision; changed dates → time-dependent; 5xx, timeouts or slow failures → external dependency). The model gets a guide to each pattern's signature and the whole test-file format, and a fix that breaks the YAML or cannot be made goes back with the lint explanation or the check to name (task `analyze-flaky` v2).
- **Attempt to fix** applies the fix and runs the test 5 times through the ordinary runner; the review shows the verdict (*Stable: passed 5/5*, *Still flaky*, *Failing*), then **Keep the fix** or **Undo**. `testpion ai run analyze-flaky --item test:<path>[:<step>]`, `testpion ai attempt-fix <id> [--times 5] [--allow-production]`; MCP `ai_analyze_flaky`, `ai_attempt_fix`.

**Rules** change the traffic on the way: **capture only** (only what they match is listed), **filter out** (hidden), **highlight** (a colour by host, URL, program, status, time or size; errors, slow and large stand out from the start), **modify** (headers set or removed, a body replaced, a delay), **reply** (a canned response, the server never sees it), **redirect** (another host or scheme) and **breakpoints** (the request or the response pauses in a dialog for editing, then goes on or is aborted). Globs or regular expressions match; presets add the usual ones (a header, CORS, no cache, slow network, offline, a canned 200, redirect to localhost, a breakpoint) for the selected host, and a row's **Rule** menu adds **Reply with this response from now on**. Rules live in profiles saved in the workspace (`debugger/rules.json`, committed, shared through git); a test box says what the rules would do to a URL; filter presets; **Compare** two exchanges side by side. For agents: `debugger_rules`; for the terminal: `testpion debug --rules debugger/rules.json`.

**HTTPS decryption**: a root certificate made on this computer (fingerprint, trust in one click, remove, export, renew) lets the Debugger read the HTTPS of programs that trust it; hosts can stay encrypted; a program that does not trust it shows as a failed tunnel with the reason. **WebSocket** connections show every frame both ways, **Server-Sent Events** every event, live. **Fiddler .saz** sessions open. A **Convert** panel decodes and encodes URL-encoding, Base64, hex, HTML, timestamps, JWTs and JSON. `testpion debug --decrypt` and `debugger_capture { decrypt: true }` do the same from the terminal and for agents. Agents get `debugger_capture`, `debugger_exchanges`, `debugger_exchange`, `debugger_session`, `debugger_rules` and `debugger_stats`; the terminal gets `testpion debug [-p port] [--lan] [-o session.har] [--rules file] [--decrypt] [--json]`.

**HTTP/2 and gRPC**: programs that speak HTTP/2 are read as HTTP/2 (streams on a **Connections** tab, grouped by connection); **gRPC** calls are captured even without TLS (gRPC clients tunnel plaintext HTTP/2 through a proxy), with their status from the trailers and every message both ways as JSON, decoded with the workspace's `.proto` files or field by field. **A phone or another computer**: the Capture menu shows this computer's addresses with QR codes; the page they open has the proxy settings and, when HTTPS is decrypted, the root certificate to install. `testpion debug -w .` decodes gRPC with the workspace's protos.

**The workbench** (laid out like HTTP Debugger Pro): a **tool rail** (Submitter, Filter, Highlight, Auto-Reply, Modify, Timeline F5, Summary, Structure F6, Performance, Convert, Export/Import); a dense **grid** (#, Offset, Duration, Method, Version, URL, Status, Type, Size, Speed, Application, Domain, IP Address, User, PID on demand) sorted by any column, columns chosen, several rows selected with Ctrl/Shift; **Request Details** and **Response Details** side by side with Header / Content / Raw / JSON tabs; a **dock** of panels: **Filter** (Filter Out and **Capture Only** rules, each with its hits), **Highlight** and the **Highlight Rule** editor (a condition on a column, colours per theme, bold, whole row), **Auto-Reply**, **Modify**, **Timeline** (sending / waiting / receiving, several requests on one axis), **Summary**, **Structure** (domains and paths), **Performance** and **Convert**; a right-click menu that turns a row's program, URL, domain, method or IP into a rule; **Incoming requests** from TestPion's mock servers; All Applications / All Domains / All Types filters, an HTTPS-inspection banner and totals in the footer. Every exchange records the program's process id, the server's address and the send time. A long capture stays quick: the list holds the whole 5,000-exchange session and gets only what changed (a new request is one row, not the list again). A request in **Incoming** opens in the same panes with what the mock answered; saved sessions (HAR) keep the new columns; **Save content** writes a body to a file; the docs have a screenshot of it all.

While the proxy runs, the **status bar** says so wherever you are: the port, how many rules change traffic, and whether the system proxy points at TestPion (in the warning colour when something changes traffic); a click opens the Debugger.

### Kafka
**Kafka** joins WebSocket, Socket.IO, MQTT and SSE in the realtime editor: brokers (`kafka://host:9092`, SASL and TLS), topics to read (new messages or from the beginning, with a consumer group), and **Produce** with a key, a partition and message headers. Each message shows its topic, partition@offset, key and headers. Saved Kafka connections run in collections and test files (`mode: kafka`), `testpion kafka <brokers>` reads and produces from the terminal, and agents use `realtime_exchange`. The example workspace has a Kafka demo (`clinic.events`) and `tests/kafka/clinic-events.yaml`.

### AsyncAPI import
An AsyncAPI 2 or 3 document imports as a collection of **connections**, one per channel: Kafka topics to produce to (with the example message, its key and headers) and to read, MQTT topics to publish to and subscribe to (with their QoS), WebSocket paths and Socket.IO events. Every message of a channel is kept to send again, built from its example or its schema; the servers become an environment.

**Export ▸ AsyncAPI 3.0** (`testpion export -f asyncapi`) goes the other way: a collection's connections become a document, with their saved messages as examples.

A realtime test can check what it received against the document: the `asyncapi` check fails a message that matches none of its channel's messages, and says what is wrong.

### .http files
`.http` / `.rest` files from VS Code's REST Client and the JetBrains HTTP Client import as collections: file variables, request names, chained tokens (`{{login.response.body.$.token}}`) and JetBrains response handlers, which run as written. **Export ▸ .http file** (`testpion export -f http`) writes a collection back for those tools.

### Generate test data
**Generate…** in the Collection Runner makes rows of realistic data from an API operation's request body or a JSON schema (emails, names, cities, prices, dates, enum values, numbers in range), saves them in `datasets/` and runs with them. `testpion generate-data` and `generate_dataset` do the same.

### Data from PostgreSQL and MySQL
A data-driven test file or a collection run can take its rows from **PostgreSQL** or **MySQL / MariaDB**: a `postgres://` or `mysql://` URL, or `env:NAME` for an OS variable that holds it, with a query. The query must be one SELECT and runs in a read-only transaction. In the Collection Runner, **Database…** takes the URL (`{{variables}}` resolve, so the password can stay a secret variable) and lists the tables. `testpion run-collection -d postgres://… --iteration-query "SELECT …"` and the `run_collection` tool take the same.

### API definitions: Preview and Lint
An API definition's **Preview** reads like its docs: operations by tag with their parameters, request body and responses, schemas as short type outlines, and **Open as request**. `testpion openapi-ops` lists them in a terminal; agents use `openapi_outline`.

An API definition has a **Lint** tab: broken `$ref`s, path parameters that are undeclared or not required, duplicate operationIds, undefined security schemes, operations without responses, examples that don't match their schema, missing operationIds or success responses and more, each marked in the editor as you type. A row shows the place; **How to fix (AI)** asks the assistant for the changes. `testpion openapi-lint` checks files, folders or the workspace's `specs/` for CI (exit 1 on errors, `--fail-on warning`), and agents use `openapi_lint`.

AsyncAPI documents are listed under API definitions too, with a Preview of their channels and **Generate tests** (a realtime test per channel).

**Generate tests** on the Preview writes a first suite: a test file per tag with each operation's example (its documented status, the OpenAPI contract, latency) and one invalid request that must get a 4xx. `testpion tests-from-spec` and `generate_tests` do the same.

### Fuzz an API
An API definition's **Fuzz** tab sends each operation its valid example, then requests that break one rule of the schema at a time: a required field left out, a wrong type, a value outside its enum, range, length or format, a body that isn't JSON. It finds **server errors** (a 5xx on bad input), **invalid input accepted** (validation the API is missing) and statuses the document doesn't list; **Explain and fix (AI)** says where to look. **Save as tests** keeps each finding as a regression test that expects a 4xx. `testpion fuzz` does it in CI (exit 1 on server errors, `--save-tests`) and agents use `api_fuzz`. Local and private-network hosts only unless you allow others; never with a production environment; DELETE only when you include it.

### GraphQL subscriptions in tests
A test file or a collection run with a `subscription` subscribes, waits for the first event (or `events:` of them, at most `wait:` ms) and checks it like a query's response: `$.data…` for the first event, `$.events` and `$.count` for all. A subscription that gets no event fails with the reason.

### Secrets from 1Password, Vault, AWS, Azure and Google Cloud
An environment variable can hold a reference instead of a secret: `op://Clinic/API/credential`, `vault://secret/clinic#apiKey`, `aws-sm://prod/clinic#apiKey`, `azure-kv://clinic-kv/api-key` or `gcp-sm://my-project/api-key`. TestPion reads it with the manager's own command-line tool, signed in as you, when a request needs it; the reference is safe to commit and the value is never written anywhere. The first time, the app shows the exact commands and asks before running them. `testpion secrets <environment>` checks the references in CI.

## 0.2.0 — 2026-09-27

Postman parity: most of Postman's day-to-day features, plus AI help and an MCP server for AI agents. Workspaces from 0.1.0 open unchanged.

- **Folder scripts and variables.** **Edit folder** (in a folder's ⋯ menu) sets pre-request and post-response scripts, variables and auth for every request inside. Scripts run collection → outer folders → folder → request, in tabs, the Collection Runner and the CLI. Inner folder variables win, and request and data variables win over folder variables. Folder scripts and variables round-trip through Postman v2.1.
- **`pm.sendRequest`.** Scripts can send HTTP requests (URL or Postman request object, raw or URL-encoded bodies) and use the response in a callback, including chained requests. Requests share the run's cookie jar, respect timeouts and cancellation, are limited to 20 per script, and are listed in the Console. Monaco typings and a snippet are included.
- **AI help in the request builder.** **Describe a request** turns plain words into a request in a new tab, using variable names but never values. **Generate tests** appends AI-written `pm.test` checks, labelled as AI-generated, to the Post-response script. **Explain** on 4xx/5xx responses opens the assistant with the likely cause and fix. Model output is parsed and validated, and nothing runs until you choose to.
- **For AI agents.** `fluxpion mcp-server` serves a workspace to AI agents (Claude Code, IDE assistants …) over MCP with seven tools: list collections, requests and environments, read a request or the collection docs, send a request (saved or ad hoc) and run a collection. Output is redacted, variable values are never listed, production environments need `--allow-production`, and `--read-only` removes sending. The docs site publishes `llms.txt`.
- **Postman-like sidebar.** The REST view's sidebar has Collections, Environments (click to activate, edit, create) and History (grouped by day, click to open) panes, and friendlier empty states.
- **Home and environment quick look.** A new **Home** view, which the app opens on the first time, has quick actions (new request, GraphQL, import, new collection, MCP, AI, assistant, docs), recent requests, collections (with run) and environments (click to activate), plus keyboard shortcuts. An eye button next to the environment selector shows the active environment's and the global variables with initial and current values, secrets masked.
- **Tabs and history.** Request tabs have a right-click menu: pin (pinned tabs stay first and survive bulk closes), duplicate, close, close others, close to the right and close all, with one confirmation for unsaved changes. History is grouped by day (Today, Yesterday, weekday, date), and double-clicking an entry reopens it.
- **Console.** A Postman-style console in the bottom panel (status bar **Console** or Ctrl+Alt+C). It lists every request (from tabs and runs) with status, time and size, shows script `console.log` output under each request, and expands to request and response headers and bodies. It has All / Errors / With logs filters and search. Everything is redacted, including values echoed back by the server, and nothing is written to disk.
- **Export to Postman v2.1.** Collections export as Postman v2.1 (folders, requests, params, path variables, headers, all body types, bearer/basic/API key/OAuth 2.0 auth, scripts, variables, descriptions, examples and settings), and environments as Postman environments (secret values never included). Status assertions become `pm.test`s, and anything Postman can't hold is listed. Available from the Export menus and as `fluxpion export` / `fluxpion export-environment`. The Postman importer now also reads collection-level scripts, path variables, OAuth 2.0, GraphQL and file bodies, and the redirect/TLS settings, so export and import round-trip.
- **Examples (saved responses).** Save a response as a named example of a request with **Save as example**. Browse, rename and delete examples in the request's new **Examples** tab. Examples are stored in the collection file with sensitive headers, JSON fields and secret values masked. Postman imports bring saved responses in as examples, and request descriptions too.
- **Documentation.** Each request has a **Docs** tab for Markdown with a live preview. The collection's **Docs** tab (formerly *Overview*) renders the whole collection as one page: description, table of contents, and every request's URL, auth, parameters, headers, body and examples, with sensitive values masked. **Export Markdown** saves the page, and `fluxpion docs <collection>` writes the same from the CLI. Markdown is sanitised before it is shown.
- **Mock servers.** A collection's **Mock** tab serves its saved examples on localhost. It matches method and path (`:id` / variable segments, literal paths first, flexible ids), picks examples with `x-mock-response-name` / `x-mock-response-code`, adds CORS headers, logs requests live and follows example changes. The same is available from the CLI as `fluxpion mock <collection>`, which also accepts Postman collection files.
- **Cookie jar and cookie manager.** Each workspace has a cookie jar. Cookies from `Set-Cookie` responses are stored, including those set during redirects (login flows), and sent with later matching requests, following RFC 6265 domain, path, `Secure` and expiry rules. A request's own Cookies tab still wins for the same name. A **Cookies** dialog (cookie button next to Send) lists cookies by domain and lets you add, edit, delete and clear them. The jar is kept on this machine only, encrypted with the OS credential store, and is never written to workspace files. Scripts get `pm.cookies.jar()` (`get`, `getAll`, `set`, `unset`, `clear`), and `pm.cookies` now includes jar cookies in runs too. The HTTP and GraphQL requests of a run share one jar.

Fixed a Windows crash of the CLI at exit.
- **Collection Runner.** Runs a collection or folder in order, with iterations, CSV/JSON data files (`pm.iterationData`), a delay, a request checklist, "Keep variable values" and "Stop on first failure". Supports `pm.execution.setNextRequest`, `postman.setNextRequest` and `pm.execution.skipRequest()`. Collection-level scripts run before each request's scripts.

Pre-request scripts can change the outgoing request. Values set by scripts are kept as local "current values" (sensitive ones encrypted), never in workspace files. A Scripts panel with snippets and `pm` typings.
- **Request builder.** Paste a cURL command into the URL bar to import it. Code snippets in 15 languages and tools, with secrets masked by default.
